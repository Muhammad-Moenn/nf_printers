# Taste
- Wants styling driven by semantic design tokens — reusable CSS variables in the global stylesheet (`--color-primary`, `--color-heading`, `--font-family`, `--font-size-xl`, `--font-weight-bold`, spacing, radii, shadows) — and considers hardcoded colors, font families, font sizes or other tokenizable values in components unacceptable; existing global variables should be reused rather than duplicated or overwritten. Confidence: 0.9
- Prefers minimal, tightly scoped changes: when adding a feature or tweaking a default, explicitly preserve the existing behavior (filtering, searching, pagination, query caching, existing UI) exactly, don't duplicate components, and don't touch unrelated sections. Confidence: 0.65
- Wants newly built/redesigned sections to visually match the sections already redesigned — same font sizes, colors and color scheme (shared badge/heading/card tokens) — instead of introducing a new visual style. Confidence: 0.7
- Wants a single, shared section-heading style across all landing sections — identical font size scale, font weight, leading/tracking and color — instead of per-section variations; flags it when headings differ between sections. Confidence: 0.75
- Wants one key word (or phrase) of each section heading highlighted in the hero's brand blue accent color, applied consistently across all sections' headings. Confidence: 0.65
- Wants sections fully animated on scroll: reveal animations trigger when the section first enters the viewport (`whileInView` with `once: true`), not only on mount. Confidence: 0.65
- Expects every section to be fully responsive across mobile/desktop breakpoints and correctly styled in both light and dark mode, and treats interactive UI (e.g. a slider with prev/next controls, autoplay, dots) as incomplete unless it actually works. Confidence: 0.6
- Prefers large refactors/migrations done incrementally: one feature at a time, tested and stable before moving to the next, rather than converting everything at once — but the end state must be complete across the whole surface (e.g. every page of the dashboard), and will call out a partial migration as unfinished. Confidence: 0.7
- Justifies data-fetching/caching work by end-user performance — fast rendering and fast content display across the app — so treat coverage gaps (uncached pages, duplicate/stale fetches) as the priority, not just the one page being edited; redundant fetches (e.g. a mutation refetch plus the realtime echo of the same write) are reported as "wasteful" defects to fix even when the UI is functionally correct. Confidence: 0.7
- Dislikes unnecessary type assertions / unchecked casts (`as X`, `as unknown as Y`) used to silence mismatches: expects the underlying types to be corrected instead (e.g. real DTOs and normalization at the boundary), and never wants errors hidden by weakening types or disabling existing checks. Confidence: 0.65
- Wants hard approval gates between phases/scope areas: complete one area, deliver a detailed report, then stop and wait for explicit approval before touching the next area — approval of the overall task is not authorization to expand scope. Confidence: 0.7
- Prefers imagery displayed directly on the page surface — no surrounding card/box/panel frame — and scaled up larger, as long as the layout stays unbroken and responsive. Confidence: 0.6
- When reviewing performance/optimization work, wants an exhaustive item-by-item status of what is actually implemented versus only partially done, plus the concrete places it can break or was not verified — not just a summary of changes. Confidence: 0.55
- Wants a single source of truth for shared identifiers: keys/paths defined by a factory (e.g. `queryKeys`) must be reused everywhere rather than re-typed as inline literals, and treats duplicated literals as a drift risk that will silently break dependent logic (invalidation) later. Confidence: 0.6
- Wants cache/query invalidation to cover every variant of a parameterized key rather than the single current value: e.g. clear year-scoped entries for the current *and* previous year (to survive a rollover) and derive shared parameters such as a `topServices` limit from one exported constant, treating "can silently stay stale" variants as a defect worth fixing. Confidence: 0.6
- Insists optimization work be evidence-driven and phase-by-phase: establish a measured baseline before changing code, never fabricate numbers, change one mechanism at a time so the improvement is attributable, and report real before/after measurements. Confidence: 0.7
- Proactively surfaces latent security/session-correctness gaps (e.g. authorization only checked on full load, so a mid-session role change goes unreflected) and hands them over as "fix this if it should be" — expecting an honest judgment on whether it is a real defect, the warranted fix rather than a blanket one, and the residual risk stated explicitly. Confidence: 0.55
